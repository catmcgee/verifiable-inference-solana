1 · STREAM anchor — the bandwidth the encryption eats

Median STREAM triad bandwidth on the box (theoretical: ~614 GB/s from 12× DDR5-6400). CPU LLM decode is memory-bandwidth-bound, so this is the mechanism the TEE tax is measured against. The headline number is the matched pair — two identical 32-vCPU VMs differing only in SEV state: SEV-ES AES memory encryption costs 26% of deliverable bandwidth (346.2 → 256.1 GB/s). Note this 26% is the bandwidth tax; the actual single-stream decode tax below is far smaller because a single decode stream does not saturate the bus. The SNP CVM anchor (376.9 GB/s, KDS-verified, separate run) is shown for context only — a different kernel/day, not a matched SEV-off↔SNP pair, so no SNP tax is claimed from it.

2 · TEE inference tax — overhead per model, matched cell

The measured SEV-ES inference tax, at the one cell where legs A and B were run identically (single-stream, 32 threads, short prompt; concurrency 1). Tax = (median tokens/s leg A − median tokens/s leg B) / leg A. (8b-q8, glm-5.2-q4 were not run on both legs at this cell, so no tax is shown for them.)

The result is the surprising part: decode throughput is taxed only about 2% at its worst here — far below the 26% STREAM bandwidth tax above. The reason is in that STREAM number: single-stream decode at 32 threads does not saturate memory bandwidth, so SEV's encryption cost on the memory path hides in the slack. The 26% STREAM figure is a pure-bandwidth bound, not the tax a single decode stream necessarily pays. This historical SEV-ES chart does not extrapolate beyond its one matched cell; the newer cloned-twin SNP matrix, including isolated concurrency cells, is reported separately below.

11 · Honest limits

What is and isn't protected, stated plainly. "Encrypted" is layered.

  • SNP is live, but the measured software chain is incomplete: the live guest returns a VMPL0 report whose signature verifies through the AMD VCEK→ASK→ARK chain and whose launch measurement is policy-allowlisted. Report data binds the ephemeral signing key plus guest-declared registry and build digests. The root disk is mutable and the build digest is a release identifier, not a measurement of every Python module and weight byte, so this does not independently prove which model implementation ran. A measured immutable root/code manifest is required to close that gap.
  • The input-sealed path removes prompt plaintext from the TLS proxy: HPKE on /v1/infer_sealed seals only the prompt to the SNP-bound key; its response is plaintext inside the outer TLS connection. Use /v1/chat_e2e for a response sealed back to the verified client. Neither mode defends against an operator who replaces the mutable guest application with one that logs plaintext.
  • Metadata leaks: request timing, sizes, model choice, token counts, and cost are visible to the operator/network even when the payload is sealed. Traffic analysis is not addressed.
  • Model weights are public by design — hashed into the receipt, not hidden. Leg C (Claude proxy) is deliberately not private: Anthropic sees plaintext; it's the honest control.
  • On-chain is hashes, not content: only sha256(prompt), sha256(response), model hash go to Solana — a commitment, not the text (an adversary who guesses the text can confirm it).
  • Trust roots include AMD and the measured guest supply chain: AMD's ASP/PSP, memory-encryption engine, RMP, and VCEK→ASK→ARK chain are hardware roots. The verifier also relies on the launch-measurement policy, firmware, guest image construction, and currently the operator-controlled mutable disk. SNP does not address all side channels or traffic analysis.
  • When a GPU arrives: re-run the same matrix and report measured results separately. This report makes no GPU overhead or zkML throughput projection without data.

Method notes

Aggregation is median throughout, with p99 where tails matter (ITL, attestation phases). Harness convention: n ≥ 5 runs per A/B/C cell targets n ≥ 10; leg D targets n = 5. The first 2 raw records per cell are discarded during aggregation. Raw JSONL is immutable and includes those requests; sparse cells stay visible rather than being erased. Legs A and B differ only in SEV state: same kernel, model files, thread pinning (numa_policy recorded per request), and runtime versions. Leg D encodes the ladder rung in the model field because the frozen v1 schema has no rung field. Charts derive exclusively from the two input files; every chart lists the run_ids behind it.
