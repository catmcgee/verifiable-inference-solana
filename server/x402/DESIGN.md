# Payment design v2 — token-metered via Solana session intent

DECISION (Cat, 2026-07-16): pricing is **token-based**, implemented with the
HTTP Payment Authentication **session intent** for Solana
(https://paymentauth.org/draft-solana-session-00.html) instead of naive
per-request x402 pay-first. This supersedes ADDON-REGISTRY.md step 4's
"settled upfront, no metered refund" limitation — sessions exist precisely to
meter unknown-length streaming output like LLM inference.

## Why sessions fit inference

Per-request pay-first forces quoting `max_tokens × out_price` and keeping the
overage. Sessions instead:
- client opens a channel (on-chain escrow PDA, one tx), then
- signs **cumulative-amount vouchers** off-chain per request/stream chunk, and
- the server meters actual tokens: `available = acceptedCumulative − spent`;
  when a stream approaches the authorized balance it pauses and requests a
  higher voucher (client can top up mid-stream), and
- settlement is one on-chain tx at close (`settleAndFinalize` + `distribute`).
Exact-usage billing, two on-chain txs per session total, funds held by the
channel program (not us), client recovers unspent funds via forced close.

## Mapping to our stack

- Challenge (402): price from models.yaml (`price_per_1m_{in,out}_usdc`,
  GENERATED by pricing.py). `unitType` = tokens; in/out distinction rides the
  quote: cost = prompt_tokens×in + streamed_tokens×out, recomputed as we serve.
- Metering point: `server/x402/` middleware wraps POST /v1/chat/completions;
  debit per streamed token using the same client-measured token events the
  metrics already count. Free endpoints stay free.
- Vouchers: 48-byte Borsh (channel ‖ cumulative u64 ‖ expiry i64), ed25519.
  Verification pattern is IDENTICAL to our post_receipt introspection — reuse
  the sysvar-introspection code path style in any on-program work.
- Receipts: our attested-inference receipt (prompt/response/model hashes,
  enclave sig) rides alongside the spec's `Payment-Receipt` header — the
  differentiator ("attested inference") is unchanged.
- Listing (payskill/generate_listing.py): advertise session intent support +
  token prices; regenerate before P5 publish, validator rules apply.

## Implementation order (P5)

1. Channel program: use the reference implementation/program from the draft's
   ecosystem if deployable; write our own only if none is usable on devnet.
2. Middleware: challenge → open → voucher-per-request happy path (no streaming
   pause) → streaming pause/top-up → cooperative close → forced-close handling.
3. Devnet e2e with the demo client, then wire into the listing.

Open items: which cluster (devnet first), grace period (spec recommends 15m),
splits (none initially — single payee), fee sponsorship (start without).
